# Subscriptions & Integration (M1)

What the subscriptions app does, how to use it, and the integration issues found
while walking the full journey. Accounts/products are documented in
[ACCOUNTS_PRODUCTS.md](ACCOUNTS_PRODUCTS.md).

## Run it

```bash
python manage.py migrate
python manage.py test subscriptions
python manage.py close_expired_subscriptions          # schedule daily
python manage.py close_expired_subscriptions --date 2026-12-31
```

## Lifecycle

```
Draft ──send quote──▶ Quotation ──confirm──▶ Confirmed ──activate──▶ Active ⇄ Paused
  ▲                       │                                         │  (pause/resume)
  └──── quote expired ────┘                                         ├─ renew ─▶ Active (term extended)
                                                                    └─ close ─▶ Closed ─ renew ─▶ Active
any open status ──close──▶ Closed
```

| Action | From | Rule | Who |
|---|---|---|---|
| Send quote | Draft | needs lines; sets `quotation_expiry` = today + template validity (default 30 days, `SUBSCRIPTION_QUOTE_VALIDITY_DAYS`) | staff |
| Confirm | Quotation | quote not expired; an expired quote goes back to Draft | staff, owning customer |
| Activate | Confirmed | needs lines, expiry not passed; `next_billing_date` = start date | staff |
| Pause | Active | `plan.pausable` | staff, owning customer |
| Resume | Paused | not past expiry | staff, owning customer |
| Renew | Active, Closed | `plan.renewable`, has an expiry; extends by the original term length | staff, owning customer |
| Close | any open | Active/Paused before expiry needs `plan.closable` | staff, owning customer |
| Auto-close | Active, Paused | past expiry and `plan.auto_close` (command or API) | system |

Every successful change writes a `SubscriptionStatusChange` row (from, to, user,
reason, time) in the same transaction. Failed actions change nothing.

All rules are in `subscriptions/services.py`. Views, the portal (`sub.pause()` etc.
on the model delegate to services) and the management command all call it.

## Data

- **Subscription**: `number` (SUB-0001, generated by the backend), customer, plan,
  template, status, start/expiry date, quotation expiry, payment terms,
  next billing date, notes.
- **SubscriptionLine**: product, variant, quantity (≥ plan minimum), unit price
  (defaults: plan price for the plan's own product, otherwise sales price; plus
  the variant's extra price), tax rule (defaults to the product's).
  `line.plan` mirrors `subscription.plan` because billing and the dashboard read it.
- **QuotationTemplate / TemplateLine**: plan, lines, validity days, optional term
  in months. Subscriptions created from a template get their own copy of the lines.

## API (`/api/subscriptions/`)

| Method | URL | Notes |
|---|---|---|
| GET | `/` | `?search=` (number, customer name/email) `&status=` `&plan=` `&customer=` |
| POST | `/` | `{customer, plan, start_date, expiry_date?, payment_terms?, notes?, lines: [{product, variant?, quantity, unit_price?, tax_rule?}]}` |
| GET, PATCH, PUT | `/{id}/` | edit only while Draft; `lines` replaces all lines |
| POST | `/{id}/send-quote/` | optional `{validity_days}` |
| POST | `/{id}/confirm/`, `/activate/`, `/renew/` | |
| POST | `/{id}/pause/`, `/resume/`, `/close/` | optional `{reason}` |
| GET | `/{id}/history/` | status changes, oldest first |
| POST | `/close-expired/` | staff; returns `{closed: [numbers], count}` |
| CRUD | `/quotation-templates/` | staff; nested `lines` |
| POST | `/quotation-templates/{id}/create-subscription/` | `{customer, start_date}` |

Rule violations return `400 {"detail": "..."}` (or `{"<field>": ["..."]}`).
Customers get only their own subscriptions; anyone else's id is a 404.

Staff pages: `/subscriptions/` (search, status/plan/customer filters, CSV) and
`/subscriptions/<id>/` (lines, totals, history, action buttons).

### Open issues for module owners

1. **`Plan.billing_cycle` no longer exists** (M2 renamed it to `billing_period`:
   daily/weekly/monthly/yearly). Still used in `billing/services.py:211`
   (`run_billing`), `billing.services.calculate_period` (expects
   monthly/quarterly/annually, so daily and weekly need adding),
   `dashboard/views_web.py:23` (MRR), `dashboard/management/commands/seed_data.py`, `billing/tests.py`.
   Owners: M3, M4.
2. **`User.username` / `first_name` / `get_full_name` no longer exist** (M2 uses
   `name` + `email`). Still used in `billing/serializers.py` (63, 85, 101, 133),
   `billing/services.py` (236, 292, 460, 497), `billing/views.py:85` (search),
   billing/dashboard/portal templates, `seed_data.py`, and `billing/tests.py`
   (`create_user(username=...)`, which is why 5 billing tests error). Owners: M3, M4.
3. **Typo in billing line dict**: `billing/services.py` around line 131 builds the key
   `"des   pricecription"` but line 266 reads `l["description"]`, so a real billing
   run raises `KeyError` even after 1 is fixed. Owner: M3.
4. **Invoice lines should use `line.product`**: billing builds the description
   from `line.plan.product.name`. `plan.product` is optional in M2, so this crashes
   for plans with no product. Use `line.product.name` (the line's product is now
   always set). Owner: M3.
5. **Portal "Accept" button**: `portal/templates/portal/my_subscriptions.html:31`
   shows Accept for `draft`. Customers accept a **quotation**, so the check should be
   `sub.status == 'quotation'`. The model's `accept()` already maps to confirm.
   Owner: M4.
6. **Duplicate auth pages**: M4's `accounts/views_web.py` and `accounts/web_urls.py`, and
   `products/views_web.py` and `products/web_urls.py`, duplicate M2's pages under the same
   URL namespaces, so they are unmounted in `config/urls.py`. They can be deleted
   once M4 agrees. Owners: M2, M4.
7. **Auth scheme**: the architecture says JWT, but the code (M2) uses DRF
   `TokenAuthentication`. Subscriptions follows the code. Team decision needed.
8. **`config/settings.py` / `manage.py`** carry a hard-coded
   `C:\Users\lenovo\...\python.exe` path (from the billing update commit). It's harmless
   but machine-specific. Owner: M3.
